# Deployment-readiness decisions and integration work

The current application is a verified local fictional-data MVP release candidate. The approved v2 full-year class-summary request passed the sustained 90-student workload at 475 ms p95 against the 500 ms target; legacy v1 retains its earlier failed measurement. Nothing here selects a provider, grants approval for real student data, or constitutes a production deployment. `scripts/validate-deployment.mjs` validates provider-independent pilot, fictional staging and production environment shapes; production deliberately fails until a school identity adapter is implemented.

## Exact work after the external choices

1. Obtain approved provider/region, identity protocol and privacy/retention decisions. Record accepted values and responsible people in `DECISIONS.md` without committing credentials.
2. Implement a versioned school identity adapter at the current server boundary, including teacher provisioning, student/class mapping, revocation, session rotation and failed-login controls. Keep the local adapter restricted to fictional pilot use. Add provider sandbox contract and cross-tenant tests before any real student record.
3. Provision isolated hosting, PostgreSQL, TLS origin and secret storage through approved infrastructure. Run migrations on a new service, set the validated environment, and confirm production startup fails closed when any required setting is absent. Test reverse-proxy observed address handling for throttling and trusted forwarding rules.
4. Establish archive/ledger/key custody and approved retention periods. Rehearse backup, wrong-key rejection, empty-target restore, deletion replay, restored access reconciliation and report/reward comparison on fictional production-like infrastructure. Record recovery time and failure handling.
5. Run the owner/device/AT/network review checklist, repair defects, repeat integrated suites and obtain written school release approval. Only then schedule a controlled classroom pilot with real identities/data.

Local preflight example: create private directories outside this repository and obtain three distinct keys from the responsible custodian. Set `DATABASE_URL`, `PVF_ORIGIN`, `PVF_AUTH`, `PVF_RECEIPT_KEY`, `PVF_BACKUP_KEY`, `PVF_DELETION_LEDGER_KEY`, `PVF_BACKUP_DIRECTORY`, `PVF_DELETION_LEDGER`, `PVF_RETENTION_DAYS`, `PVF_BACKUP_RETENTION_DAYS`, and `PVF_AUDIT_RETENTION_DAYS`; run `node scripts/validate-deployment.mjs pilot`. The script checks syntax, paths and key separation without connecting to or changing the database. `production` returns a named identity-adapter blocker by design. Do not put keys or connection passwords into the command line, test logs or repository.

For a private fictional-data staging service, the repository includes a `Dockerfile` and one-process staging runtime. The host supplies PostgreSQL, an HTTPS `PVF_ORIGIN`, distinct private keys, and first-start `PVF_STAGING_TEACHER_USERNAME`/`PVF_STAGING_TEACHER_PASSWORD` secrets. The runtime requires `PVF_MODE=staging`, `PVF_AUTH=local` and `PVF_FICTIONAL_ONLY=true`; it builds and serves the SPA with the API, migrates forward, provisions at most one fictional teacher without printing its password, and exposes `/api/healthz`. This is an MVP review surface only. The current machine has no connected hosting CLI and its saved GitHub credential is invalid, so provider upload remains pending.
